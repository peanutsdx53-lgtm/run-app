## 承認済みの対象・判定規則

## 機能設計根拠 WHAT／WHY
- 現行では「基本情報」→「詳細情報（5件、休養日は2件）」→共有保存前の確認（出所・保存する内容・位置情報の保存可否）→保存ボタンの順。詳細情報が長い/編集に往復した場合、本人が保存直前に見るべき対象は既存`saveReviewScope()`であり、新しい重複の保存説明パネルではない。
- 提供するのは同一画面の移動だけ。本人の`recordDraft`、GPS同意、保存ID、保存元、本人記述、未入力と0、保存ガード、二重タップ排他、ローカル原本、結果3タブ、科学参考値を一切変更しない。
- GPSプレビューはこの画面では保存できない。GPSで「保存する内容」を保証する誤った案内はしない。休養日の保存は走行と別の契約のまま。
- 必須入力不足とプライバシー説明は従来の場所に保持し、スクロールやフォーカス移動が保存可否判定を変えない。

## 画面設計根拠 HOW／WHY
- 既存「詳細情報」の末尾に、一つだけ「保存する内容と出所を確認する」（GPSは「保存可否と出所を確認する」）という48px以上の操作を追加する。ユーザーが選んだときだけ既存の保存内容カードへスクロールし、`tabindex="-1"`のターゲットにキーボードフォーカスを移す。
- 「保存前の確認」は`saveReviewScope()`原文をそのまま内包する一つの`id="rr-save-scope"`ターゲット。新たなハッシュリンクはSPAルートを壊すので使わない。新しい保存操作や保存済み扱いは作らない。
- 画面幅320/390/768/1440、root文字通常/200%、日本語/English、Chromium/WebKitの基本32条件で、操作語とフォーカス、欠け・横はみ出し、元の必須警告・ローカル保存源・個人情報詳細を実ブラウザで点検する。
- 追加は全幅用の折返し・ボタンサイズの最低限CSSのみ。過去に除外した正常時の重複「入力内容を確認しました」カードを復活させない。既存レビューの必須3バッジやエラーカードを隠したり折りたたまない。
